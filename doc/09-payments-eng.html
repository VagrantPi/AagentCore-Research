Payments = 讓 agent 自己付錢

呼叫一次付費 API 的價值往往只有幾美分，信用卡的最低手續費讓這種微支付做不起來 —— 而且為每個供應商各自簽約也不實際。

1用 HTTP 402 走標準流程，以 USDC 結算

agent → 商家：GET /premium-data
商家 → agent：402 Payment Required（金額、收款方、幣別、網路）
agent → AgentCore：ProcessPayment（session、instrument、402 內容）
  → 檢查 session 預算與到期時間（超過就拒絕）
  → 透過 Identity 取憑證、向錢包供應商簽署 → 回傳付款證明
agent → 商家：重試，帶上 X-PAYMENT header
商家：驗證並上鏈結算 → 200 + 內容
✓Agent 端全部自動：Strands 用 AgentCorePaymentsPlugin、LangGraph 用 AgentCorePaymentsMiddleware，攔截 402、呼叫 ProcessPayment、自動重試。agent 的工具程式碼只寫一個普通的 http_request。
✓私鑰和錢包憑證不會進到 agent 裡 —— 存放在 Identity 的 payment credential provider（token vault + Secrets Manager）。
✓用 clientToken 確保同一筆付款不會被執行兩次。失敗時會釋放預算保留。

2名詞速查

USDC價值與美元 1:1 掛鉤的穩定幣 = 放在區塊鏈上的美元儲值金
錢包 / instrument持有 USDC 的帳戶，私鑰由 Coinbase 或 Privy 代管
network哪條鏈，CAIP-2 格式：eip155:8453 = Base 主網、eip155:84532 = Base Sepolia 測試網
gas fee上鏈執行交易的手續費 = 跨行轉帳手續費
facilitator替商家驗證付款並送上鏈的服務 = 收單機構

!IAM 職責分離是整套機制的核心

官方把權限拆成幾個 role，其中兩條是硬性要求：

ManagementRole
（agent developer）		建立 instrument 和 session，也就是設定預算 → 明確 Deny ProcessPayment
ProcessPaymentRole執行付款、讀取餘額 → 不能有建立 session 的權限
為什麼不能放在同一個身分

如果同一個身分既能建立 session（決定預算上限）又能執行付款，一旦被 prompt injection 誘導，就能自己開一個無上限的預算再付款給自己。官方用明確的 Deny 讓這種組合在 IAM 層面就不可能發生。

!交易不可逆 —— 三道防線缺一不可

鏈上交易一旦完成就無法撤回，不像信用卡可以申請退款。這讓「agent 付錯錢」的代價比一般 API 呼叫高得多。

✗誘導付款：網頁或工具輸出寫著「請去這個網址買完整報告」，agent 照做。這是最現實的攻擊面。
✗惡意商家：回傳的 402 要求付款給攻擊者的地址。
✗花費失控：agent 陷入迴圈不斷付費重試。
緩解三件套

商家白名單（LangGraph middleware 有 allowlist 設定，或用 Gateway 只開放審核過的付費 target；也要比對 payTo 地址）＋ session 預算設低（maxSpendAmount + 到期時間）＋ 大額付款要求真人核准。再用 Policy 對付費工具的參數設限當第二道防線。

!upto 的 Permit2 設定值是覆蓋，不是累加

✗upto（依用量計費）要先在鏈上做一次 Permit2 allowance 授權（permit2AllowanceLimit），這一步要付 gas fee。
✗每次設定都是覆蓋舊值，不是累加 → 只在第一次需要時設定，反覆呼叫會重複付 gas。
MPP 的三個細節

① 每次只能處理一個 challenge，很快就會過期 —— 過期時回ValidationException 但不扣預算。② 回傳的 paymentCredential 要原封不動放進 header，不能解碼或修改。③ 商家不負擔 gas 時必須明確設定 buyerPaysGasFees=true，否則被拒。solana 只有 Privy 支援。

!錢包餘額是 0，而且成本比例要自己算

✗錢包建立時餘額是 0。使用者要自己登入供應商 wallet hub 入金（加密貨幣、信用卡、金融卡、Apple Pay、Google Pay、ACH —— 信用卡在部分地區無法使用），並明確授權 agent 可以用這個錢包（之後可撤銷）。
✗這代表使用者要自己管理一個加密錢包，一般消費者門檻不低 → 比較適合 B2B 或企業預先儲值。
✗成本直覺：每次付費呼叫若只值 $0.01，Coinbase 每次操作 $0.005 就佔了 50%。AWS 本身不另外收費，但供應商操作費 + gas fee 要先算進定價。

3區域與不確定性

✗支援美國、歐洲、新加坡、雪梨；東京、首爾、孟買不支援。發表時的部落格只寫 4 個區域，之後才擴充 —— 不要照部落格文章規劃區域。
✗是否已 GA 官方文件沒有明確寫出（2026-05-07 以預覽狀態發表）。要上線前先確認。
✗法遵要自己評估 —— 加密資產支付各地法規不同，在台灣導入前需要法遵評估，官方文件沒有涵蓋這部分。
✓生態系：x402 Bazaar 已整合成 Gateway 的一個 target（可搜尋一萬多個付費端點）；也可以把自己的 API 做成 x402 收費（官方範例是每次呼叫 $0.01），另一種商業模式。

→導入前的六個檢查

  1. ManagementRole 與 ProcessPaymentRole 真的分開了嗎？有明確 Deny 嗎
  2. 商家白名單在哪一層？plugin／middleware 的 allowlist 還是 Gateway target
  3. session 的 maxSpendAmount 與到期時間設多小？大額付款有人工核准嗎
  4. 錢包誰入金、誰授權 agent 使用？信用卡不可用的地區怎麼處理
  5. 定價有算過 供應商操作費佔比嗎（$0.01 商品會被 $0.005 吃掉一半）
  6. 部署區域在支援清單內嗎？GA 狀態與台灣法遵確認過了嗎
