Gateway = agent 流量的單一入口

定位從「把 API 轉成 MCP 工具」擴大成三合一：MCP 聚合器、HTTP 代理、LLM 代理。

← 02 Memory 03 Gateway目錄 04 Identity →

1三種 target，能力不同

Agent ──► Gateway ──┬── MCP       /mcp 聚合後端成一個虛擬 MCP server
   （inbound 驗證）    │        Lambda、API GW stage、OpenAPI、Smithy、
                       │        遠端 MCP server、內建 connector
                       ├── HTTP      /<target>/… 直接轉送，不做協定轉換
                       │        Runtime、A2A、任意 HTTP 端點
                       └── Inference  依 model 欄位轉送（LLM 代理）
✗HTTP target 不支援能力同步與語意搜尋。
✗Runtime target 只能加到沒有設定 protocolType 的 gateway。
✓Inference target 可直接用 OpenAI / Anthropic SDK 呼叫，換模型只改 model 字串。

!Inbound 四選一，其中兩種不授權

CUSTOM_JWT驗 JWT；缺 scope 回 403 + WWW-Authenticate，client 可自動探索
AWS_IAM驗 SigV4 + 檢查 InvokeGateway
AUTHENTICATE_ONLY只驗簽章，完全不做授權
NONE什麼都不檢查
選了後兩種，就 Anyone Can Invoke

必須另外搭 Policy（Cedar）、interceptor，或由後端自行授權。NONE 可以用 bedrock-agentcore:GatewayAuthorizerType 這個 condition key 在組織層級直接禁掉。

另外：JWT 的 sub 會進 CloudTrail → 別放個資，用 GUID。

2Service role 是所有 target 共用的

✗它的權限就是任何呼叫者透過這個 gateway 能碰到的上限。共用一個 gateway 等於把不同信任等級的後端綁在同一組權限上。
✓官方做法：不同信任等級的 target 拆成不同 gateway，各自 service role。
✓Outbound 用 OAuth On-behalf-of（OBO）：拿使用者 token 換一張範圍更小、audience 只限目標服務的新 token，下游每層都能各自授權。token 直通只給 PoC。

3四種治理手段怎麼分工

Policy（Cedar）授權：工具被呼叫前做確定性 allow / deny。宣告式、可稽核 → 這是安全邊界
Interceptor（Lambda）加工：改寫請求／遮罩回應／短路。REQUEST 與 RESPONSE 兩階段
Rate limit防濫用：依 claim、IAM 身分、target、工具分組（最多 10 維）
Gateway rules灰度：依呼叫者或路徑導向 target、切換 bundle、依權重分流
Rate limit 預設 fail-open

限流服務不可用或維度解析失敗時請求直接放行 → 不能當安全機制，只能當成本與防濫用。變更最多 30 秒生效。

Interceptor 受 Lambda 6 MB payload 上限限制，大回應要用 payload filter 排除 body；HTTP target 的 interceptor 不支援串流，MCP 串流時則每個事件都會被呼叫一次。

4AWS Agent Registry（組織層級的目錄）

Gateway 解決「流量怎麼進來」，Registry 解決「組織內到底有哪些東西可以用」。它是官方元件清單裡唯一在這個 repo 沒有獨立資料夾的一員。

收錄什麼MCP server、agent（依 A2A schema 驗證）、skill，以及自訂類型（API、Lambda、KB、DB 等，搭配自訂的 metadata schema）
審核流程送審 → EventBridge 通知 → 走你既有的審核流程 → 呼叫 UpdateRegistryRecordStatus 核准或退回。過時的項目可以標成 deprecated，下架後就搜尋不到；開發環境可以設定自動核准
搜尋語意搜尋和關鍵字搜尋同時進行；每個 registry 都自帶一個 MCP 端點，coding assistant 可以直接連上來搜
同步從外部 MCP server 的 URL 抓名稱和工具說明，每次同步都會產生一個新版本
組織整合搭配 AWS Organizations，可以自動偵測所有成員帳號的 Runtime 和 Gateway 並建檔；也可以用 RAM 跨帳號分享
驗證搜尋和 MCP 端點可以用 IAM 或 JWT；控制面永遠用 IAM
區域us-east-1、us-west-2、愛爾蘭、雪梨、東京
分工：Registry 負責「找」，Gateway 負責「用」

「找」是組織內有哪些工具和 agent 可用、而且已通過審核；「用」才是實際的連線、驗證與治理。⚠️ 預覽版的 bedrock-agentcore namespace 將在 2026-10-30 停止支援，要遷到新的 agent-registry。

Registry 不會幫你驗證、授權或限流——找到之後要真的接上線，還是得回前面那幾張卡：連線與憑證在「Service role 是共用」、授權在「四種治理手段」、速率上限在「配額與死線」。

5工具多了會變貴又變笨

✗每個工具的名稱、說明、參數 schema 每次呼叫模型都要送。兩個內建工具就≈900 token；幾百個工具 = 每次幾萬 token，而且模型會選錯工具。
✓開語意搜尋：agent 多一個 x_amz_bedrock_agentcore_search，先搜再呼叫。
✗但搜尋只支援 MCP target（DYNAMIC 模式不行），且預設每分鐘只有 25 次。

6target 與工具的三個細節

✗遠端 MCP server 用 DEFAULT 同步模式時，後端工具有變動要自己呼叫 SynchronizeGatewayTargets，否則 agent 看到的是舊清單（非同步，大型目錄要幾分鐘）。DYNAMIC 則不能搭語意搜尋與 3LO。
✗工具名稱會被加上 ${target}___${tool} 前綴（三個底線），你的 handler 要自己剝掉。
✗MCP 2026-07-28 是無狀態的，requestState 要你的 server 自己驗證是否屬於同一個使用者，Gateway 不檢查。

!配額與死線

200 TPS 是整個帳號共用的

每個 gateway 200 TPS，整個帳號也是 200 TPS；並發 5,000 同樣共用。拆成多個 gateway 不會增加總額度——最容易被忽略的一條。

2026-10-30 · Registry 預覽版 namespace 停用

舊的 bedrock-agentcore namespace 停止支援，需遷移到 agent-registry。

其餘：每 gateway 100 targets／每 target 1,000 工具、逾時 15 分鐘、payload 6 MB、rate limit 50 條、gateway rules 20 條（依權重分流只能 2 組）。

→三個設計決定

  1. Inbound 選哪一種？→ 要安全邊界就用 JWT / IAM，不要用需要別人補救的 AUTHENTICATE_ONLY
  2. 一個 gateway 還是多個？→ 不同信任等級拆開，因為 service role 共用
  3. 授權靠哪一層？→ Policy（Cedar）；rate limit 不是安全機制
