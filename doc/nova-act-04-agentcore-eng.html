疊在 AgentCore 上面，不是取代它

Nova Act 負責「看畫面、決定下一步」；AgentCore 提供跑程式的地方、雲端瀏覽器、身分、觀測、工具入口。

區域：Nova Act 服務只在 us-east-1

Runtime 與 Browser 可以放其他區域，但每一步模型推論都要跨區呼叫 us-east-1 —— 這段跨區延遲是每次操作都要付的。

2Runtime：ARM64 與兩條執行長度

# cdk/agentcore/handler.py 的骨架
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from bedrock_agentcore.tools.browser_client import browser_session
from nova_act import NovaAct   # 官方指南寫成 nova_act_sdk，是錯的

app = BedrockAgentCoreApp()

@app.entrypoint
def handler(payload):
    with browser_session(region) as client:             # 開 Browser session
        ws_url, headers = client.generate_ws_headers()  # CDP 端點 + SigV4 header
        with NovaAct(starting_page=payload["starting_page"],
                     cdp_endpoint_url=ws_url, cdp_headers=headers,
                     headless=True, clone_user_data_dir=False) as nova:
            return {"status": "success", "response": str(nova.act(payload["prompt"]))}
!容器是 ARM64：Runtime 的 microVM 模式只支援 ARM64，Instances 模式才支援 x86_64。
!時長上限：microVM 最長 8 小時、Instances 最長 14 天。HITL 等待時間算在裡面。

瀏覽器放 AgentCore Browser、而不是塞在 Runtime 容器裡：映像檔不用裝 Chromium、可用 Live View／DCV 讓真人接手、瀏覽器在隔離 microVM 裡。代價是多一段網路延遲，加上跨作業系統的鍵盤問題。

!Browser：三種接法，四個坑

寫法適合
browser_session(region) ＋ generate_ws_headers()最簡單，CDK 範例用的就是這個
AgentCoreBrowserSessionProvider(profile=...)，再傳 browser_auth=provider需要跨 run 保存登入狀態（cookie、localStorage 存在 profile）
自訂 AgentCoreBrowserActuator把開關 session 藏起來，workflow 程式碼完全不用改
!跨 OS 鍵盤問題：SDK 在 macOS、Browser 在 Linux 時，ControlOrMeta+A（全選）這類快捷鍵可能對應錯誤，影響 agent_type()。README 說這是「跨 OS 架構的預期行為」—— 把 SDK 也部署到 Linux 就沒這問題。
✗NovaAct(proxy=...) 對 CDP 端點無效 —— 要改用 AgentCore Browser 自己的 proxy 設定。
!一個 Browser session 只能有一條 automation stream：一個 NovaAct 對應一個 session，平行執行時要各開一個（上限同時 1,000 個）。
✗Profile 就是登入憑證：用 IAM 限制誰能讀寫；存檔時是整個覆蓋，平行的 session 不要共用同一個 profile 寫回。

!官方 Identity 範例把 OAuth token 寫進 prompt

# 官方使用者指南的寫法
@requires_access_token(provider_name="custom-oauth-provider")
def automate_customer_outreach(*, access_token: str): ...

browser.act(f"Use OAuth token {access_token} to: 1. Log into the site ...")
                              ^^^^^^^ token 交給了模型
這違反同一份指南自己的 Data protection 建議

token 會送到 Nova Act 服務、出現在 agent trajectory 裡；有設 S3 匯出的話也會被寫進去。而 FAQ 說模型有 guardrail 不處理密碼類輸入 —— 所以這個範例能不能跑成功本身就有疑問。

正確做法：token 留在程式碼層

① 用 Playwright 設 header（nova.page.context.set_extra_http_headers(...)）或塞 cookie；② 或 act() 只負責點到欄位，再用 nova.page.keyboard.type(token) 輸入。需要代表使用者時走 Identity 的 3LO 流程並做好 session binding。

!官方範例把 CDP 的認證 header 寫進 log

位置問題建議
cdk/agentcore/handler.pylogger.info(f"headers are {headers}") —— 把 SigV4 認證 header 寫進 CloudWatch刪掉；log 的存取權限也要收緊
同上用 NOVA_ACT_API_KEY 驗證，但同一份 CDK 總覽寫「All examples use IAM Role authentication」正式環境改用 Workflow ＋ IAM
使用者指南 Identity 範例from nova_act_sdk import NovaAct —— 套件名稱是錯的改成 from nova_act import NovaAct
同上NovaAct() 沒傳 starting_page，但它是必填參數補上
examples/agentcore前置條件要求「full access」權限正式環境縮小權限

共通點：官方範例的定位是示範，不是可以直接部署的模板。SigV4 header 進 log 這類問題在參考實作裡很常見，code review 時要當成標配檢查。

3Observability：三套紀錄用同一個 session ID 串

1裝 aws-opentelemetry-distro，設 AGENT_OBSERVABILITY_ENABLED=true、OTEL_PYTHON_DISTRO=aws_distro（在 Runtime 上大多已預設）。
2nova.start() 後用 nova.get_session_id() 取 session ID，放進 OTel baggage：baggage.set_baggage("session.id", sid)。
3ADOT 自動埋點把 trace 送到 CloudWatch 的 GenAI Observability 儀表板。
能串起三套紀錄，但有個未確認點

同一個 session ID 可對上：AgentCore trace、Nova Act Console 的 step 紀錄、CloudWatch AWS/NovaAct 指標。官方範例只示範了 baggage，沒有說明 Nova Act 的每一步會不會自動變成 span —— 需要實測。

4Gateway：兩個方向，第二個比較有用

方向做法狀態
Nova Act 當 clientworkflow 連到既有 Gateway，把 MCP 工具傳給 NovaAct(tools=...)工具功能還是 Preview
Nova Act 當工具把 workflow 掛到 Gateway，讓其他 agent 當成一個工具呼叫官方說可以，細節看 Gateway 指南

第二個方向是讓組織內其他 agent 共用瀏覽器自動化能力最乾淨的方式：像「在供應商入口網站查訂單狀態」這樣的 workflow 只維護一份，所有 agent 透過 Gateway 使用，再加 Policy 控制誰能呼叫。

5成本：Nova Act 吃掉 97%

項目5 分鐘流程估算
Nova Act agent hour$4.75 × 5/60 ≈ $0.396
AgentCore Browser（1 vCPU / 4 GB）CPU 滿載上限 ≈ $0.0075 ＋ 記憶體 ≈ $0.0032 ≈ $0.011
AgentCore Runtime（等推論的 I/O 時間不收 CPU）通常 < $0.005
省錢的關鍵是減少步數與 act 的時間，不是壓 AgentCore 的資源

AgentCore 帶來的額外成本幾乎可以忽略 —— 優化 Runtime 規格的效益大概只有千分之一。耗時又長又沒結果，通常是 prompt 沒拆小。

→動工前的六個檢查

  1. OAuth token 有沒有被寫進 prompt —— 那是官方範例的錯，token 應該留在程式碼層
  2. log 裡有沒有 CDP 的 SigV4 header 或其他認證資訊 —— 官方 handler 就有這行
  3. SDK 和 Browser 是否同一個作業系統 —— 跨 OS 的鍵盤對應會錯
  4. 平行的 session 有沒有共用同一個 profile 寫回 —— 存檔是整個覆蓋
  5. Runtime 是 ARM64 嗎、8 小時夠嗎 —— HITL 等待算在裡面
  6. 成本還是記憶體網路那筆帳嗎 —— 97% 在 Nova Act，優化對象是步數
