Evaluations = 針對 agent 行為的自動化測試

Agent 的錯大多是語意上的 —— 答錯、選錯工具、沒完成任務，但 HTTP 狀態碼是 200。傳統測試與監控抓不到。

1資料來源就是 06 的 trace

評估器讀取 session、trace、span，對三個層級評分：

SESSION整段對話是否達成目標
TRACE單次回答的品質（正確性、忠實度、切題、安全性…）
TOOL_CALL工具選得對不對、參數對不對

沒有開 observability 就沒有評估 —— 需要 Transaction Search + ADOT instrumentation。所以 06 是 07 唯一的資料來源。

2評估器有四種，價格差三個數量級

Built-in16 個，多數用 LLM 當評審。軌跡比對類（Trajectory*Match）是程式判斷，不花 token
Third-partyDeepEval、AutoEval，AWS 代管執行
Custom LLM-as-judge自訂評分指示與量表，可選模型
Code-basedLambda 寫確定性規則：JSON 格式、個資洩漏（regex）、是否呼叫禁用 API
✗Built-in 的數量三種說法：文件寫 16 個、定價頁寫 13 個、文件另列 17 個評審範本。不要在文件或程式裡寫死數量。
✗Code-based 輸入是整個 session 的 span，超過 6 MB 會被截斷 → 長 session 可能看不到完整資料。Lambda 最長 300 秒。
✓關鍵指標優先用確定性方法（code-based、軌跡比對），把 LLM 評審留給沒有確定性答案的品質面向。

!Ground truth 只能離線用

Ground truth（標準答案、斷言、預期工具順序）只能用在離線評估 —— 線上正式流量沒有標準答案。

用了 ground truth placeholder 的自訂評估器，不能放進 online 評估

規劃 online 設定時要先確認每個評估器的 placeholder。

自訂評估器一旦被啟用中的 online 設定引用，就會被鎖住

不能修改或刪除（不只 code-based，LLM 評審一樣）。要改先停用設定，或複製一份新的。改 prompt 的迭代節奏會被這個鎖定拖慢。

3五種執行模式

Online正式流量抽樣持續評分。不能用 ground truth；每設定最多 25 個評估器，每帳號最多 1,000 個設定
On-demand指定 trace／session。要先等 CloudWatch 收進資料，約 2–5 分鐘；每請求只能用 1 個評估器
Batch改動前後比較、回歸測試。token 單價 75 折；同時只能跑 5 個，每 job 最多 500 個 session
DatasetRunner 實際呼叫 agent再評分 ≈ 整合測試（預覽）
SimulationLLM 扮演使用者多輪對話。只能用 assertions，扮演者的模型費另計
導入順序

開發期 on-demand + dataset 進 CI → 上線前 simulation 擴大覆蓋 → 上線後 online 抽樣監控 → 每次改 prompt 前後用 batch 比較。

!LLM 評審本身不可全信

評審也是 LLM，分數會有雜訊和偏誤 —— 例如偏好比較長的回答，或偏好跟自己同一系列的模型。

✓看趨勢和分布，不要看單一分數；定期抽樣人工複核校準。
✗孟買與新加坡的內建評估器速率只有其他區域的六分之一（200 次 vs 1,200 次／分鐘），不可調整 → 把這些區域的評估流量算進容量規劃。
✗內建評估器可能跨區域推論執行 → 有資料駐留要求時要先確認。

4Optimization 閉環

trace → Recommendations（新的 system prompt / 工具說明）
     → configuration bundle（不可變、有版本的設定快照）
     → Gateway rules 分流 A/B test（附統計顯著性）→ 全量上線

Configuration bundle 把「agent 的行為設定」從程式碼抽出來：Gateway 用 W3C baggage header（aws.agentcore.configbundle_arn）告訴 Runtime 用哪個版本，agent 端用 BedrockAgentCoreContext.get_config_bundle() 取得。

一定要設定預設值

沒有 A/B test 時會拿到空的 dict，而 API 呼叫失敗時會直接拋出例外。兩種狀況都會讓 agent 起不來。

✗每個 gateway 同時只能跑 1 個 A/B test，而且只能分成兩組（對照組 + 一個實驗組）；每個帳號同時最多 20 個。
✓Insights 預覽期免費；Recommendations 本身免費，只收它用到的 Evaluations 費用。

5配額與計費

Built-in每千 input token $0.0024 / 每千 output token $0.012
自訂評估器每千次評估 $1.50，模型費用另計
單次上限每次 200,000 input token；每 session 20,000 span、200 MB

成本直覺：評審要讀完整對話上下文，所以長對話的評估成本跟著上下文長度增加。Online 的抽樣比例與評估器數量是主要的成本控制手段。

→導入前的五個檢查

  1. Transaction Search 與 ADOT 都到位了嗎？沒有 trace 就沒有評估
  2. 關鍵指標有確定性的評估器（code-based／軌跡比對）嗎？還是全部靠 LLM 評審
  3. 自訂評估器有沒有被鎖住？改 prompt 前先確認它沒被啟用中的 online 設定引用
  4. CI 裡的 on-demand 有加 2–5 分鐘等待嗎？
  5. 孟買／新加坡的六分之一速率有算進容量規劃嗎？
