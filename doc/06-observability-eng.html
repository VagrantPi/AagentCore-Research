Observability = 唯一能還原「它當時為什麼這樣做」的東西

同樣的輸入，模型每次可能走不同路徑 → 「重現問題」很困難，trace 是事後唯一的依據。

1Agent 的三個「不一樣」

錯誤很多是語意上的：回答錯了、選錯工具、陷入迴圈，但 HTTP 狀態碼是 200
延遲主要來自模型推論，而且跟輸出的 token 數量成正比
成本與 token 用量成正比，同一個請求的差異可能到百倍 → 必須逐次追蹤

所以 trace 除了時間，還要記下模型輸入輸出、選了哪個工具、工具的參數和結果、token 用量。這也是 07 Evaluations 能自動評分的原始資料 —— 沒有 observability 就沒辦法做線上評估。

2三層資料模型與存放位置

Session（session.id，透過 header 或 OTel baggage 傳遞）
└── Trace（一次 invoke）
      └── Span 樹
            ├── InvokeAgentRuntime      服務自動產生
            ├── agent loop              框架產生，需要 ADOT
            │     ├── chat / invoke_model  模型名稱、token 數
            │     └── execute_tool         工具名稱、參數、結果
            └── Memory / Gateway / Identity 各服務自行產生

全部走 OTel 標準並遵循 GenAI semantic conventions（OTel 為 LLM 定義的屬性名稱）。

✓新 agent 的 span 在 /aws/bedrock-agentcore/runtimes/<agent_id>-<endpoint> 的 spans stream —— 每個 agent 各自獨立，所以能針對個別 agent 設存取權限與 KMS 加密。舊 agent 在共用的 aws/spans，可用 UNIFIED_TRACES_DESTINATION_ENABLED 切換。
✗Memory、Gateway、內建工具的 log delivery 要自己設定（CloudWatch Logs / S3 / Firehose），預設不會送出。

!兩個開關，沒開就看不到東西

① 帳號層級：沒開 CloudWatch Transaction Search 就看不到 span

一次性設定，但所有 agent 共用 —— 最容易漏掉的一步。

② 程式層級：ADOT 版本要 ≥ 0.18.0

Runtime、Memory、Gateway、Identity 的 metric 與服務端 span 服務會自動給；但 agent「內部」的 span（呼叫模型、呼叫工具）不在自動範圍內，要靠 aws-opentelemetry-distro>=0.18.0 加上去。

Harness 是例外 —— 預設全開，不需要任何設定。

!APPLICATION_LOGS 會記錄完整 payload

APPLICATION_LOGS 記錄每次呼叫的 trace / span ID，再加上 request_payload 和 response_payload。加上 span 本身也可能含 prompt 與工具輸入輸出 —— 等於把使用者的對話內容全部寫進 CloudWatch。

✓Log group 用 KMS CMK 加密，依法規設保留天數；用 CloudWatch 的資料保護政策遮罩個資（會額外收費）。
✓用「每個 agent 獨立 log group」把存取權限限縮到負責該 agent 的團隊。
✗不想讓 prompt 落地，就不要開 APPLICATION_LOGS，或在前端加一道遮罩。
✓USAGE_LOGS 記錄每個 session 每秒的用量 → 可以把成本分攤到個別 session 或使用者。

!這個變數的名字和效果相反

AWS_GENAI_CONTENT_EXTRACTION_OPT_OUT=true —— 名稱看起來像「不要擷取內容」，但官方說法是「讓模型的 payload 和工具的請求與回應保留在 span 上」。

上線前一定要實測

確認 span 裡到底有沒有 prompt 內容。不要靠變數名稱假設隱私行為 —— 這是名稱與實際效果相反的案例。

3Metric 的兩個陷阱

✗CPUUsed-vCPUHours / MemoryUsed-GBHours 最多延遲 60 分鐘，而且不等於實際帳單。可以當趨勢看，不能當對帳依據。
✓ActiveSessionCount（目前進行中的 session 數，可依 Runtime / CodeInterpreter / Browser 篩選）→ 監控 session 配額用量，建議對它設警報（例如超過配額 80%）。別用 SessionCount，那是累計值。
✓錯誤分類：Throttles 回 429、quota 回 402（不是 429）、UserErrors 裡的 ServiceQuota 是配額告警來源。

!CloudWatch 帳單可能超過 Runtime 本身

span ingestion 約 $0.35 / GB、log 約 $0.50 / GB，另有儲存與查詢費用。而 agent 的 span 很大：含 prompt 與回應，一輪對話就可能數 KB 到數十 KB，工具結果若是長文件更大。

控制方式

① Transaction Search 的索引抽樣比例（UpdateIndexingRule）② 縮短 log 保留期限 ③ 只在需要的環境開啟 payload 記錄。

4接上與接出去

Runtime 上的 agentaws-opentelemetry-distro>=0.18.0，用 opentelemetry-instrument python main.py 啟動；框架本身要開 OTel（Strands 內建，其他框架用 OpenInference 之類的 instrumentation 套件）
AgentCore 之外
（EKS / Lambda）		同一套 ADOT 加環境變數；session ID 要透過 OTel baggage 帶入（session.id）
送到其他平台DISABLE_ADOT_OBSERVABILITY=true 取消預設 ADOT，再自行設 exporter（Datadog、Langfuse 等）
跨帳號CloudWatch OAM 的 sink 與 link；需分享 Metrics 和 Logs 兩者，且只能在同一個區域內使用
要把整條 trace 串起來

呼叫時帶上 X-Amzn-Trace-Id（X-Ray）或 traceparent（W3C）與 baggage —— 內建工具和 Identity 的 API 也接受。另外不支援 ADOT Collector，只能用 ADOT SDK 或 Lambda Layer。

→上線前的四個檢查

  1. 帳號有開 Transaction Search 嗎？ADOT 有 ≥ 0.18.0 嗎？
  2. 實測 APPLICATION_LOGS 與 span 裡實際記了什麼，不要相信變數名稱
  3. 用 ActiveSessionCount 對 session 配額設警報，不要用累計的 SessionCount
  4. CloudWatch 帳單列為獨立成本項 —— 抽樣 + 保留期限 + 只在必要環境記 payload
