Identity = 兩個身分綁在一起

Agent 比一般服務多一層：它要同時是「某個 agent」，又「代表某個使用者」。

← 03 Gateway 04 Identity目錄 05 Tools →

1模型：三個東西

使用者 JWT ──► Runtime 驗簽章 → 取 iss+sub
                          │
                          ▼
        workload access token  = AWS 簽發，同時綁定「agent + 使用者」
                          │
                          ▼
     token vault  以 (agent, user) 為 key → 第三方 OAuth token / API key
✓Runtime / Gateway 自動完成 inbound 驗證與換發，token 直接放進請求 header。你的程式碼只要加 @requires_access_token。
✗Runtime 自動建立的 workload identity 不能直接拿去換 token（官方刻意設計，防 agent 程式盜取）。只能用 header 那一張。

!ForUserId 完全不做驗證

ForJWTJWT 的 iss + sub，會驗簽章與過期時間 → 正式環境用這個
ForUserId呼叫端給的不經驗證的字串，信任完全建立在呼叫端
偽造 userId = 拿到別人的 Google / Slack token

Vault 是以 (agent, user) 為 key 存的，所以 userId 是對的話，token 就會被發給錯的人。

✗有 JWT 就明確 Deny GetWorkloadAccessTokenForUserId 與 InvokeAgentRuntimeForUser。
✗真的要用 userId，必須從已驗證的 principal 推導，絕對不能接受前端傳來的值。
✓多 IdP 時加前綴避免撞名，例如 cognito+user123。

!3LO：兩個 callback 別搞混

第三方後台註冊的是 AgentCore 的 callback（每個 credential provider 一個）
自己的 callback 註冊在 workload identity → allowedResourceOAuth2ReturnUrls

攻擊情境：使用者 A 不小心把授權 URL 傳給 B，B 按下同意後，B 的帳號就被綁到 A 的 agent session 上。

✗agentcore dev 在本機會代你處理 callback → 部署到正式環境要自己實作 CompleteResourceTokenAuth，這是最容易漏的一步。
✗Session binding 的使用者身分必須從瀏覽器當下的 session（cookie）取得，官方明確禁止從遠端 session 快取取。
✓授權 URL 與 session URI 只有 10 分鐘有效；另外帶一個不透明的 state 防 CSRF。

2Refresh token 要一家一家自己去開

✗Vault 裡有有效 refresh token 就會自動換新的 access token，不必再叫使用者按同意。但每家供應商都要各自開啟才會發：Google 要 access_type=offline、Microsoft 要 offline_access scope、GitHub / Slack 要在 app 設定裡開。
✗忘記開 → 每 1–2 小時就要重新授權一次。
✓Vault 回的 token 不保證有效：使用者可能已在第三方撤銷，而 AgentCore 不知道 → 遇 401 帶 forceAuthentication=true 重走流程。

3三種 outbound 模式

Autonomous（M2M / 2LO）Client credentials — agent 以自己的身分存取公司內部資源
User-delegated（3LO）Authorization code — 需要使用者本人同意才能讀他的資料
On-behalf-of（OBO）Token exchange（RFC 8693）— 使用者已登入你的系統，不再問同意就換到給下游的 token

正式環境用 OBO：換到的 token audience 只限下游服務，而且下游能看見「是 agent 在代表使用者操作」。最後是否核准由你的 IdP 決定。

GetResourceOauth2Token(oauth2Flow=ON_BEHALF_OF_TOKEN_EXCHANGE, workloadIdentityToken=…)

4Provider 與 workload identity 沒有強制綁定

✗官方不強制「哪個 agent 只能用哪個 credential provider」，完全靠 IAM 的 Resource 限制 → 要寫到具體的 workload identity ARN + provider ARN，敏感者再加明確 Deny。
✗回到 01 的重點：VM 裡的程式碼讀得到 execution role 憑證。agent 被 prompt injection 攻擊時，攻擊者拿到的是該 role 允許的所有 provider token（限於當前使用者）。
✓不同 agent 用不同的 workload identity 與 IAM role，各自只能碰自己需要的 provider。

5Inbound JWT authorizer

✗Runtime 與 Gateway 共用同一套設定（discovery URL ＋ audience / client / scope / 自訂 claim）。至少要設一項；多項同時設定時全部都要通過。
✓一定要設 audience — 否則其他服務的 token 也能打你的 agent。自訂 claim 規則可用 EQUALS / CONTAINS / CONTAINS_ANY。

!配額、計費與稽核盲點

Credential provider 預設只有 50 個

以帳號 + 區域計算。「每個租戶各自註冊一個 OAuth app」會很快用完 → 改成一個 provider 服務所有使用者，由 vault 依使用者分開存 token。

CloudTrail 看不到「替誰取的 token」

取 token 的事件會把 workload access token 遮蔽，所以查不出哪個 principal 替哪個 userId 取了 token → 要搭配自己的 log 或 trace span。

配額：workload identity 11,000 個、token 換發與 GetResourceOauth2Token 各 200 TPS、CompleteResourceTokenAuth 100 TPS。計費：非 AWS 資源每千次 $0.010，透過 Runtime 或 Gateway 免費。

→四個設計決定

  1. 使用者身分從哪來？→ 只有 JWT 一條路 production；ForUserId 一律 Deny
  2. 要存取使用者的第三方資料？→ OBO，不要轉傳使用者的 token
  3. refresh token 有開嗎？→ 沒開就是每 1–2 小時重新授權一次
  4. provider 怎麼切？→ 一個 provider 給所有使用者，靠 IAM Resource 綁 ARN
