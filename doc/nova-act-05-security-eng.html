問題不是「模型會不會被駭」

而是「模型看到的網頁內容能不能指揮它」。官方說有訓練模型防禦，但不保證擋得住 —— 所以設計重點是限制影響範圍。

1威脅模型：不可信內容會變成指令

          你的 prompt ──┐
                        ▼
網頁內容（不可信）──▶ Nova Act 模型 ──▶ 動作：點擊 / 輸入 / 上傳 / 呼叫工具 / 跳轉
   ▲  注入點                                        │
   │                                                ▼
   └── 惡意網站、使用者產生的內容            影響範圍 ＝ 瀏覽器登入了哪些網站
                                             ＋ 開放的檔案路徑
                                             ＋ 註冊的工具
                                             ＋ 執行環境的 IAM 權限
!Prompt injection ＝ 在模型會讀到的內容裡藏指令。類比 SQL injection，只是「資料」和「指令」混在同一段自然語言裡，沒有 prepared statement 可以用。
!Confused deputy：被 injection 操縱的 agent 本身就是一個 confused deputy —— 它拿著你的權限，替攻擊者辦事。
!Agent trajectory ＝ 一次執行的完整軌跡：prompt、每一步的截圖、模型回應。

!官方公布：有害指令拒絕率 96.4%

96.4% 意味著大約每 28 個有害指令會有 1 個沒被擋下

偏見內容拒絕率 99.5%。兩個數字都是 Amazon 自有資料集上的測試。不能只靠模型把關 —— 模型擋不住的，就要在架構層擋。

可靠度也沒有保證：同一個 prompt 不保證每次動作都一樣

例如彈窗出現的時機不同。官方評測是取 5 次的平均，不是每次都對。同一段 workflow 在壓力下可能走出不同路徑。

思路跟 AgentCore Policy 一樣：不信任模型的判斷，用確定性的規則限制它能做什麼。

2SDK 的三道預設防線

from nova_act import NovaAct, SecurityOptions
NovaAct(
    starting_page="https://portal.example.com",
    security_options=SecurityOptions(
        allowed_file_upload_paths=["/srv/job-123/uploads/*"],  # 只開放這個任務的目錄
        # allowed_file_open_paths=[...]                       # file:// 瀏覽，沒必要不要開
    ),
)
選項預設寫法
allowed_file_open_paths關閉特定目錄、檔案，或 "*"（全開，不建議）
allowed_file_upload_paths關閉同上
state_guardrail（URL 白名單）要自己加傳一個回傳 PASS／BLOCK 的函式
工具註冊—只註冊這個 workflow 需要的
✗官方警告：上傳路徑要開得越窄越好，否則惡意網頁可以誘導 agent「上傳」機器上的其他檔案，藉此外洩資料。
!prompt 裡寫「不要離開 example.company.com」只能當輔助 —— prompt 本身就可能被 injection 覆蓋。

!state_guardrail 是「到了之後才擋」

from urllib.parse import urlparse
import fnmatch
from nova_act import NovaAct, GuardrailDecision, GuardrailInputState

ALLOWED = ["portal.example.com", "*.sso.example.com"]

def url_guardrail(state: GuardrailInputState) -> GuardrailDecision:
    host = urlparse(state.browser_url).hostname
    if host and any(fnmatch.fnmatch(host, p) for p in ALLOWED):
        return GuardrailDecision.PASS
    return GuardrailDecision.BLOCK          # 預設拒絕

# 跑到白名單以外的網域，就會拋出 ActStateGuardrailError
每次觀察之後才檢查一次 —— 頁面已經載入了

如果目標網頁一載入就會觸發副作用（例如 GET 請求就會執行某個動作），guardrail 擋不住。它是「事後發現」，不是「不讓它去」。

更嚴格的做法在網路層

AgentCore Browser 的 proxy 或 VPC、自建環境的 egress proxy —— 讓連線根本到不了，才是真的擋。

!截圖會把畫面上的東西送給服務端

!做法是：act("click on the password field") → nova.page.keyboard.type(getpass()) → act("sign in")。模型有 guardrail，不處理密碼。
✗但畫面上看得到的東西都會進截圖，而截圖會送到服務端，也可能被寫進 S3 匯出。輸入卡號後要確認網頁有遮蔽顯示，或在輸入後直接結束這個畫面。
✗在沒有系統 keyring 的 Linux 上，Chromium 密碼管理器存的密碼是明文。
!保存登入狀態的 profile 等於憑證：依使用者隔離，並用 IAM 限制存取。

!兩種模式的資料條款差很多

項目IAM（AWS 服務）API key（nova.amazon.com）
適用條款AWS Service Termsnova.amazon.com Terms of Use
用你的資料訓練模型不會會收集互動資料與截圖，用來改進服務
資料刪除依 AWS 資料處理規範寄信到 nova-act@amazon.com 申請
!資料用 AWS owned key 加密（不支援 CMK）。trajectory 只暫存，要保存就用 exportConfig 寫到自己的 S3。
✗不加密的欄位：WorkflowDefinition 名稱、Workflow Run ID —— 不要在名稱裡放個資或客戶編號。
✗不支援 PrivateLink：從私有子網路呼叫 Nova Act 要經過 NAT，走公開端點。
「不支援 CMK」＋「不支援 PrivateLink」常常是採用門檻

金融、醫療這類有法遵要求的產業，評估前先確認法遵團隊能不能接受 AWS owned key 和經由 NAT 的公開端點。

3IAM：只能靠命名慣例分組

IAM 功能支援IAM 功能支援
Identity-based policy✅ABAC（tag）❌
Resource-based policy❌服務專屬 condition key❌（只有 aws:RequestedRegion）
資源層級權限✅ definition / run暫時性憑證✅
Service role❌Service-linked role✅ 只用來發指標
workflow-definition: arn:aws:nova-act:{region}:{account}:workflow-definition/{WorkflowDefinitionName}
workflow-run:        arn:aws:nova-act:{region}:{account}:workflow-definition/{name}/workflow-run/{id}
!不支援 ABAC → 無法用「tag 相同就允許」讓權限隨 workflow 自動擴充。只能靠命名慣例 ＋ ARN 萬用字元（workflow-definition/team-a-*）分組。workflow 名稱在建立之初就要設計好。
✓角色分工：平台管理者管 definition ＋ S3 匯出；每個 workflow 一個執行角色；維運／稽核只給 Get*／List*。
✗官方只有 nova-act:* 的 NovaActFullAccess 範例，要自己寫最小權限。

!官方文件自己矛盾的地方

項目Service Card配額頁／README
每個 act 最多幾步100200（max_steps 預設 30）
時間上限session 最長 30 分鐘act timeout 24 小時、run 1 週
workflow-run ARN指南範例少了 workflow-definition/{name}/ 前綴 —— 以資源表和服務授權參考為準
建立資源類 action指南說只能 *，但授權參考列出了資源類型 —— 需實測
!Service Card 的數字可能是模型或早期版本的行為邊界，配額頁是服務的 API 限制，兩者不一定是同一件事。
✓保守設計：一個 act 控制在 30 步以內（官方建議的可靠範圍）；單一 session 會超過 30 分鐘的，先實測。
✓其他細節：UA 預設含 NovaAct，建議自訂時保留；傳輸 TLS 1.2 以上；高風險領域（醫療、金融）必須自行評估風險並加人工監督。

→上線前的八個檢查

  1. 正式環境用 IAM，不用 API key —— API key 模式會收集互動資料與截圖
  2. 每個 workflow 一個執行角色，資源限定到 definition 與 run
  3. state_guardrail 採白名單、預設拒絕 —— 但記得它是事後檢查
  4. 上傳與 file:// 路徑維持關閉，或只開放單一任務目錄
  5. 密碼與 token 走 Playwright，並確認截圖不會截到卡號／個資
  6. 不可逆操作前加確定性的核准 —— 不要靠 prompt 叫模型問
  7. 法遵能不能接受 AWS owned key ＋ 走 NAT 的公開端點（不支援 CMK、PrivateLink）
  8. workflow 名稱的命名慣例定了嗎 —— 沒有 ABAC，之後只能靠名字分權限
