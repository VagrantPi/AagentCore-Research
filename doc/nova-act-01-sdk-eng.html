1最小程式與三種開發模式

with NovaAct(starting_page="https://...") as nova:
    nova.act("搜尋 rubber duck debugging")   # SDK 會開瀏覽器、跑 loop、結束後關閉
模式用法適合
Scriptwith NovaAct(...)正式腳本
Interactivenova.start() 後在 REPL 一句一句試。ctrl+x 中斷 act 但保留瀏覽器；ctrl+c 會關掉調 prompt
Asyncfrom nova_act.asyncio import NovaActasyncio 程式
✓Act trace：每個 act 結束產生一份獨立 HTML，記錄每一步截圖和動作，路徑印在 console（用 logs_directory 指定）。
!Time worked 不能對帳（官方說只是估計值）。想看 headless 瀏覽器就設 NOVA_ACT_BROWSER_ARGS="--remote-debugging-port=9222"。
✗只支援英文 prompt；不能在 Jupyter 裡用。首次執行裝 Playwright 瀏覽器約 1–2 分鐘。

2act() 做事，act_get() 做事並取資料

result = nova.act_get("Return the cheapest flight", schema=Flight.model_json_schema())
flight = Flight.model_validate(result.parsed_response)   # schema 不符會拋 ActInvalidModelGenerationError
!要拿資料就一定要傳 schema（可用 pydantic 產生），否則回傳值裡沒有 response。這層 schema 的角色就像呼叫外部 API 時的 response DTO 驗證 —— 模型輸出不保證正確。
!擷取資料要獨立一個 act。官方建議不要在同一個 act 裡「先操作再擷取」。
✓act_get("Am I logged in?", schema=BOOL_SCHEMA) 適合當流程分支的條件。
✓用 max_steps 而非 timeout（預設 30，硬上限 200）—— 每一步時間會隨服務負載與網站速度浮動。另有 observation_delay_ms 等動畫跑完再截圖。

3prompt 三原則：直接、講完整、拆小

✓直接：寫「Navigate to the routes tab」，不要寫「Let’s see what routes vta offers」。
✓講完整：條件、偏好、停在哪裡都要寫（例如「stop when you get to the payment page」）。當成交代一個不熟悉這網站的新同事。
✓拆小：前一個 act 的輸出當下一個的輸入，中間用 Python 串。不穩就再拆得更細。
!小技巧：日期用絕對日期；找不到搜尋按鈕時加「type enter to initiate the search」。

「拆小」同時改善可靠度、速度和成本。把確定性的部分（跳轉 URL、填帳密、下載）從 act 移到 Python／Playwright，是最直接的優化。

4nova.page 就是 Playwright 的 Page

需求做法為什麼不交給模型
輸入密碼／卡號act("click on the password field") 後用 nova.page.keyboard.type(getpass())模型會拒絕處理密碼
換頁nova.go_to_url(url)比 page.goto 更能等到真的載入完成
下載with nova.page.expect_download() as d: nova.act("click download")模型負責點，Playwright 接住檔案
原生對話框nova.page.on("dialog", handler)Playwright 預設會自動關掉對話框
上傳SecurityOptions(allowed_file_upload_paths=[...])預設禁止上傳，路徑開得越窄越好
用 Playwright 填了密碼就安全了嗎？沒有

如果之後的 act 截圖時密碼顯示在畫面上，還是會被截進去傳給模型。填完密碼要立刻導向不會回顯的頁面。

!重試不是冪等的 —— 可能執行兩次

類別意思怎麼處理
ActAgentError任務沒完成（ActAgentFailed、ActExceededMaxStepsError、ActInvalidModelGenerationError）改 prompt 或拆小後重試
ActClientError請求被拒（ActGuardrailsError、ActRateLimitExceededError）調整請求或降速退避
ActExecutionError本機執行失敗（ActActuationError、ActCanceledError）回報 bug
ActServerError服務端錯誤回報 bug
Workflow 預設在請求逾時時重試一次（read_timeout 60 秒）

官方提醒：同一個請求重試，可能真的被執行了兩次，費用也算兩次。後端類比 —— act 不是冪等的（idempotent），一個「送出訂單」的 act 重試可能下兩次單。

有副作用的 act，重試前先確認狀態

用 act_get(schema=BOOL_SCHEMA) 問「訂單已經送出了嗎」，確認沒送出才重試。順序是送出前檢查 → 送出 → 送出後確認。

!Workflow 是 IAM 的前提，而且有傳遞陷阱

要用 IAM 驗證就必須走 Workflow

進入時呼叫 CreateWorkflowRun，結束時 UpdateWorkflowRun，中間所有 session／act／step 都掛在這個 run 底下，Console 才能依層級呈現。API key（NOVA_ACT_API_KEY）則不需要，但互動資料會被收集。

ContextVar 不會自動傳到新的執行緒

用 @workflow decorator 時要搭配 copy_context().run，或用 get_current_workflow() 手動傳入。多 process 不支援（boto3 client 無法 pickle）。

平行 = 開多個 NovaAct 實例，上限是 5 TPS

一個實例就是一個瀏覽器、只能單執行緒。真正的瓶頸是 InvokeActStep 的 5 TPS 配額與本機能同時開幾個 Chromium，收到 ActRateLimitExceededError 要退避重試。

!保存登入狀態：四種 provider，雲端只剩兩個

本機檔案S3AgentCore Browser profileChromium profile
跨機器✗✓✓✗
localStorage需 restore_local_storage=True同左✓✓
IndexedDB／快取✗✗✗✓
加密✗（0o600）✓ SSE-KMS✓ 服務代管✗
部署到雲端時，本機檔案和 Chromium profile 在容器重啟後就消失

實際上只能選 S3 或 AgentCore Browser profile。官方看法：大多數 OAuth／SAML 登入只保存 cookie 就夠了。Chromium profile 模式下平行執行時每個實例一定要各自複製一份。

Linux 上沒有系統 keyring 時，Chromium 密碼管理器存的密碼是明文

容器環境通常沒有 keyring → 不要依賴 Chromium 的密碼管理器。

→導入前的六個檢查

  1. act_get 的 schema 有沒有真的接上（沒有 schema 就拿不到資料）
  2. 每個 prompt 有寫清楚停在哪裡嗎；拆夠小了嗎（可靠性＋速度＋成本三個都受影響）
  3. 密碼、換頁、下載、對話框、上傳都改走 nova.page 了嗎；填完密碼有立刻導向不回顯的頁面嗎
  4. 有副作用的 act 有做安全重試嗎（送出前先 act_get 問狀態）—— 逾時重試可能執行兩次、收兩次費
  5. 用了 @workflow 又有多執行緒的話，get_current_workflow() 有手動傳進去嗎
  6. 雲端部署的登入狀態是 S3 或 AgentCore Browser profile 嗎（容器重啟會 wipe 掉本機方案）
