ELI5 · Senior Engineers · Amazon Nova Act

Nova Act = 用自然語言操作網頁

你寫 nova.act("搜尋 rubber duck debugging")，模型就會看著頁面一步步操作，直到完成或放棄。可以和一般 Python、Playwright 混著寫。

1它是什麼、限制在哪

✗模型不能換。是 AWS 自家訓練的 Nova Act 模型，專為 UI 操作而生（官方宣稱在日期選擇器、下拉選單、彈窗這類難點有 >90% 內部評測分數）。
✗只有 Python。pip install nova-act，需 Python 3.10+，且不能在 Jupyter / iPython 裡用。支援 macOS、Ubuntu 22.04+、WSL2、Windows 10+。
✗只在 us-east-1。官方沒公布其他區域的時程。
!兩種身分、兩套條款：API key（nova.amazon.com 免費試玩，截圖等互動資料會被拿去改進服務）與 AWS IAM（正式服務）。正式環境要走 IAM。

官方路徑是 Playground 試玩 → 下載成 Python 腳本 → SDK／IDE 擴充開發 → nova-act deploy 自動包容器、建 ECR／S3／IAM role 部署到 AgentCore Runtime → Console 依 run → session → act → step 看紀錄。

2名詞層級（Console 就照這個呈現）

Workflow definition（在 AWS 上註冊的名字）
└── Workflow run（一次執行，概念上像 CI 的 pipeline run）
      └── Session（一個瀏覽器實例，可以多個平行）
            └── Act（一次 act() 呼叫＝交代模型一件事）
                  └── Step（截圖觀察 → 決定一個動作 → 執行）
!同一個 session 只能單執行緒。要平行就開多個 session，不是在同一個 session 裡加 goroutine。
✓step 預設最多 30 步，硬上限 200 步。HITL 是流程走到需要人核准、或 agent 卡住（例如 CAPTCHA）時轉給真人，處理完再交還。

3誰跑在哪裡 —— 最重要的一點

瀏覽器不在 Nova Act 服務裡，而是在你的程式那一端。Nova Act 服務本身只做「模型推論＋執行紀錄」兩件事。

你的 workflow 程式（Python + nova-act SDK）
  │  跑在：本機 / AgentCore Runtime 容器 / 你自己的 ECS、Lambda…
  ├─ 操作瀏覽器（Playwright / CDP）
  │     瀏覽器：本機 Chromium / 容器內 Chromium / AgentCore Browser（雲端）
  └─ 每一步把截圖送給 Nova Act 服務 ─→ 模型回傳下一個動作
        （InvokeActStep，預設 5 TPS／帳號，單次 payload 上限 5 MB）
        同時把 run / session / act 紀錄寫進服務供 Console 檢視

推論：運算與瀏覽器的成本落在你選的執行環境上 —— 這就是為什麼部署會另外產生 AgentCore Runtime、ECR、S3 的費用。跟 AgentCore 是疊上去，不是替代：Nova Act 管「決定下一步點哪裡」，Browser 給雲端瀏覽器，Runtime 跑你的程式。

!正式環境要固定 model_id

model_id行為
nova-act-latest自動追最新 GA 版。永遠不會自動跳到 preview → 開發環境用這個
nova-act-preview追最新 preview（查核時 v1.1）。SDK 太舊會退回該 SDK 支援的最新 GA 版並跳警告
nova-act-v1.0固定在 2025-12-02 的 GA 版，承諾至少支援 1 年
為什麼正式環境要固定版本號

跟鎖相依套件版本一樣道理：模型換版可能改變「同一句 prompt 會點哪裡」，而 UI 自動化對這種行為變化非常敏感。GA 至少支援 1 年，但退場通知機制官方沒說清楚。

!$4.75 / agent hour，而且 step 少就便宜

!按「agent 實際在工作的牆鐘時間」計費。平行跑幾個就算幾份；HITL 等真人回應的時間不計。Runtime／Browser／ECR／S3 另外計。
!計費頁沒有列 token 或 step 費用 → 推論是模型推論成本已含在 agent hour 裡。所以拆成小而明確的 act（FAQ 也建議這樣加速）同時省錢。
!粗估：一個 5 分鐘流程一天跑 1,000 次 ≈ 83 agent hours ≈ $396／天（還沒算 Runtime 與 Browser）。

!平行擴展會先撞到 5 TPS

InvokeActStep（模型推論）5 TPS／帳號 · 可調
其他控制面／資料面 API100 TPS／帳號 · 可調
每 act 步數 / act timeout / run timeout200 步 · 24 小時 · 1 週 · 都不可調
每 act 工具數100（tool spec 上限 350 KB）· 不可調
要跑一大批 agent 之前，先申請提高配額

假設每一步約 2–5 秒（這是假設，官方沒公布），5 TPS 大約只撐得起 10–25 個同時在跑的 session。瓶頸是模型推論，不是你的程式。

官方文件互相矛盾

配額表寫 200 步／24 小時／1 週，但 AWS AI Service Card 寫「每個任務最多 100 步、session 最長 30 分鐘」。要當成硬限制用之前，先確認哪一份是你環境實際套用的。

!它碰不到的東西

✗密碼欄位會被模型拒絕。有 guardrail，官方建議改用 Playwright API 直接填 → 密碼流程必須自己接。
✗瀏覽器本身的彈窗碰不到（例如要求位置權限的 prompt）—— 那是瀏覽器的 UI，不是網頁內容。
✗只支援瀏覽器，FAQ 明說不支援一般的 computer use（桌面應用程式）。
✗解析度超出 864×1296～1536×2304 準確度可能下降。非典型視窗大小要自己量測。

適用情境：資料輸入（沒有 API 的 CRM／ERP 表單）、資料擷取、結帳訂位、Web QA 測試（取代維護成本高的 selector 腳本）。

4跟其他方案的差別

方案誰決定下一步代價
Playwright／Selenium 腳本你寫死的 selector網站改版就壞，維護成本高
browser-use ＋ 通用 LLM通用模型（可換）按 token 計費，截圖很吃 token；準確度看模型
Nova Act專為 UI 操作的模型只有 Python、模型不能換、只在 us-east-1
AgentCore Browser（不決定，只提供瀏覽器）需要搭配任一種「大腦」

實務組合：Nova Act（大腦）＋ Playwright（密碼、下載等確定性操作）＋ AgentCore Browser（雲端瀏覽器）＋ AgentCore Runtime（跑 workflow）。選框架的成本分界在於「UI 行為變動時要不要維護」—— 網站常改就選 Nova Act，網站穩定就選腳本。

→導入前的六個檢查

  1. 目標網站有 API 嗎？有就先別用 UI 自動化
  2. InvokeActStep 配額申請提高了嗎？5 TPS 大約只撐 10–25 個平行 session
  3. model_id 固定住了嗎（正式環境不要用 latest）
  4. 密碼、彈窗、解析度這些模型碰不到的部分有 Playwright 接手嗎
  5. 算過 agent hour ＋ Runtime／ECR／S3 的合計嗎（5 分鐘 × 1,000 次／天 ≈ $396）
  6. 只用 IAM，不要拿 API key 跑正式資料（互動資料會被收集）
