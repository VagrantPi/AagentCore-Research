要人核准 ≠ 有人會核准

HITL 在機制上就是兩個內建工具 —— 所以「什麼時候找人」由模型判斷。不可逆的操作不該建立在這上面。

1HITL 兩種模式，性質完全不同

Human approvalUI takeover
真人做什麼看截圖，按「核准／拒絕」或選一個選項直接操作遠端瀏覽器
同步性非同步：送出請求，等人回覆即時：要有人在線
典型情境費用／採購核准、送出前確認CAPTCHA、登入、MFA／2FA
SDK 回呼approve(message)ui_takeover(message)
!SDK 只給介面，不是代管服務：你要自己實作 HumanInputCallbacksBase 的兩個方法。通知、審核頁、串流都要自己架。
!沒傳 human_input_callbacks，模型就不會發出「請求人類輸入」的工具呼叫。回呼只負責「怎麼找人、怎麼等」，不負責「要不要找」。

後端類比：這很像 Step Functions 的 waitForTaskToken —— 流程停在某一步，等外部回呼才繼續。

!「什麼時候找人」是模型決定的，不是你決定的

HITL 就是 SDK 內建的兩個工具，觸發條件跟一般工具一樣由 prompt 控制

所以在 prompt 裡寫「Ask for approval before clicking submit」，模型大致會照做 —— 但這是機率性行為，不是保證。

付款、送出這類不可逆操作，不要只靠 prompt

在 Python 裡硬拆成三段：① act() 走到付款頁 → ② 程式呼叫自己的核准流程（確定性）→ ③ 拿到核准後才 act() 付款。這樣核准是程式邏輯，不是一次模型判斷。

!官方建議：依情境設定逾時（登入通常要給比 CAPTCHA 更久）；被拒絕要能乾淨停下；所有 HITL 互動都要留紀錄以便稽核。

!等真人不計 Nova Act 的錢，但運算平台照收

agent hour 會扣掉 HITL 等待時間 —— 只有 Nova Act 這一層不計

容器與瀏覽器在等待期間必須一直開著（session 不能關），所以 Lambda 的 15 分鐘、AgentCore Runtime 的 8 小時上限照樣適用，運算平台的費用也照算。

長等待要設計成「可中斷」

參考實作的超時是 HITL_EXECUTION_TIMEOUT=7200（2 小時），遠超多數平台的執行上限。等待很久的流程應該考慮：存檔登入狀態 → 結束 session → 核准後重開。

2UI takeover：雲端只有一條路

瀏覽器在哪真人怎麼接手
本機、有畫面（headed）直接在螢幕上操作
headless開 --remote-debugging-port，把 devtoolsFrontendUrl 傳給真人（遠端主機要另外 port forwarding）
AgentCore BrowserAgentCore Console 的 Live View，或 HIS 的 DCV 串流（只傳加密後的畫面像素）
暴露 CDP 除錯埠，等於把瀏覽器的完整控制權交出去

那條路只適合本機除錯。正式環境的 UI takeover 實際上只能走 AgentCore Browser + DCV。

!工具是 Preview：本地函式好寫，MCP 要借 Strands

# 本地工具：@tool 裝飾普通 Python 函式
@tool
def read_row_as_dict(file_path: str, row_number: int) -> dict:
    """Reads a specific row from an Excel file and returns it as a dict.
    Args:  file_path (str) / row_number (int, 1-based)
    Returns: dict — column header -> value
    """
...
!docstring 就是給模型看的說明書 —— 描述、參數、回傳型別要寫清楚。寫得爛，模型就選錯工具。
!服務端上限：每個 act 最多 100 個工具、tool spec 總大小 350 KB。但官方建議越少越好，工具多了模型會選錯。
!要直接操作瀏覽器的工具設 requires_unlocked_actuator_context = True —— SDK 會在執行期間暫停自己對瀏覽器的控制（HITL 就是這樣運作的）。
✗MCP 要借用 Strands 的 MCPClient，所以必須安裝 strands-agents。官方說支援 remote MCP，官方範例用的卻是本機 stdio server —— 遠端 MCP 要自己接。
✗不需要瀏覽器時，要在 prompt 明寫「Ignore the web browser; do not click, scroll, type」，否則模型可能還是去操作網頁。

Tool use 還是 Preview，正式環境不要依賴它。

3反過來：把 Nova Act 當成 Strands 的一個工具

# Strands 當大腦，Nova Act 當工具
@tool
def browser_automation_tool(starting_url: str, instr: str) -> str:
    with NovaAct(starting_page=starting_url) as browser:
        return str(browser.act_get(instr, max_steps=10).response)

agent = Agent(tools=[browser_automation_tool])  # Strands 用 Bedrock 通用模型
✓分工：Strands 的 LLM 負責規劃推理（去哪個網站、做什麼），Nova Act 負責在網頁上把事情做完。
!執行位置：Nova Act SDK 跟 Strands agent 跑在同一台機器、同一個容器裡。瀏覽器要不要放到 AgentCore Browser，要自己在工具內設定。
✗成本是兩份：Strands 那層 LLM 按 token 計，Nova Act 那層按 agent hour 計。上層 LLM 可能反覆呼叫工具，所以一定要設 max_steps 上限（範例是 10）。
✓官方範例把例外吃掉、回傳錯誤字串，讓上層 LLM 自己決定要重試還是換做法。

4三種架構怎麼選

架構誰是大腦適合
純 Nova Act workflowPython ＋ Nova Act 模型流程固定、以網頁操作為主（填單、擷取、QA）
Nova Act ＋ 工具（Preview）Nova Act 模型網頁流程中需要少量外部資料（查 Excel、查 API）
Strands ＋ Nova Act 當工具通用 LLM需要跨系統推理，網頁只是其中一個步驟
分界線：Nova Act 的強項是「看畫面、操作 UI」

需要大量工具編排的推理（查 A、比對 B、決定 C）交給通用 LLM 的 agent，再把 Nova Act 當成它的一個工具。多加一層 LLM 是換來推理能力，代價是兩份成本。

→動工前的五個檢查

  1. 不可逆操作是不是只靠 prompt 叫模型核准 —— 應該在 Python 裡拆成確定性流程
  2. 等待真人時段有沒有算進平台的執行上限 —— Nova Act 不收費，Lambda 15 分鐘照樣砍
  3. UI takeover 在正式環境走哪條路 —— 只能是 AgentCore Browser ＋ DCV，不能開 CDP
  4. HIS 是用 Administrator 權限部署的嗎 —— 換成 AssumeExecutionRole 最小權限
  5. 加了上層 LLM 嗎 —— 那是兩份成本，而且工具要自己設 max_steps
