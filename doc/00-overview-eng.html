總覽 = agent 專用的執行平台

12 個元件、四層職責。它不是框架也不是模型，而是一組把 agent 跑起來、把關、管好、看得見的託管基礎設施。

1定位：模型不綁、框架不綁、元件可單獨用

AgentCore 是 AWS 為 AI agent 準備的一組託管服務，定位像 agent 專用的 Lambda ＋ API Gateway，再加上 Cognito、CloudWatch 這類周邊的組合包。

✓模型不綁：Bedrock 上的 Claude 可以，OpenAI、Gemini 也可以 —— agent 自己去呼叫供應商。
✓框架不綁：LangGraph、Strands，或者自己寫迴圈都行。
✓元件可單獨使用：只想用 Memory，agent 跑在自己的 EKS 上也沒問題。

名詞對齊（用後端概念理解）：agent loop 本質就是 while (!done) { ... }，只是控制流程由 LLM 在執行期決定；tool 是帶 OpenAPI 描述的 endpoint；MCP 是工具界的 USB 介面（或 LSP 之於編輯器）；session 等同 web session；token 約 0.75 個英文單字或 1–2 個中文字；LLM 則是很聰明但無狀態、不保證輸出一致的外部 API。

3為什麼不能直接丟到 Lambda

元件的設計對應的是 agent 工作負載的四個特性 —— 每一項都是一般 serverless 服務處理起來很吃力的地方：

1執行時間長、大部分時間在等：一次任務可能要呼叫十幾次模型，總長從數分鐘到數小時，但 CPU 大多閒著。Lambda 最長只跑 15 分鐘，而且等待時間一樣計費。
2有狀態：多輪對話要在同一個環境累積上下文和檔案。
3行為不確定：同輸入不保證同輸出，而且 agent 可能執行它自己產生的程式碼 → 所以要每 session 硬隔離（microVM），出事時影響範圍也控制得住。
4一定會碰到外部系統：要代替使用者存取 Slack、GitHub，憑證管理和授權就是核心問題，不是附加功能。

!一個請求怎麼走：Policy 掛在 Gateway，不是掛在 agent

以「客服 agent 幫忙查訂單並退款」為例：使用者帶 JWT 或 SigV4 呼叫 Runtime → Identity 驗證 inbound → 讀 Memory → 進入 agent loop：問模型要呼叫什麼 → 模型說 refund(order=123) → Gateway 先問 Policy 這個人能不能呼叫 refund（Cedar 評估 JWT claims） → 拿到後端的 OAuth token → 真的打 API → 結果餵回模型 → 迴圈結束 → 寫回 Memory 並非同步萃取長期記憶。

兩個關鍵事實

① 授權發生在工具被呼叫之前，而且由確定性的程式規則決定，不交給 LLM 判斷 —— 就算模型被 prompt injection 騙了，也繞不過這道檢查。② 模型呼叫不經過 AgentCore，agent 自己去呼叫供應商，token 費用另外算。

4Harness vs Runtime：最重要的一個選擇

HarnessRuntime
agent loop 由誰寫AWS 提供（底層是 Strands Agents）你自己寫（任何框架，或不用框架）
怎麼定義 agent設定檔：model、system prompt、tools、memory、limits程式碼 ＋ BedrockAgentCoreApp entrypoint，打包成 ARM64 container 或 zip

官方建議先用 Harness，有明確理由才自己掌控 loop（例如既有 agent 程式碼要搬過來）。Harness 也能匯出成 Strands 程式碼再改用 Runtime 部署，所以不算單向綁定 —— 兩者共用 Runtime 的配額，Harness 底層就跑在 Runtime 上。

!計費：大宗不是運算，是 token

全部按用量計費，沒有最低消費。一個 session 試算：1 vCPU 實際運算 60 秒、2 GB 記憶體維持 5 分鐘 → CPU 約 $0.0015 ＋ 記憶體約 $0.0016 ≈ 每 session $0.003。實務上模型的 token 費用通常才是大宗，而且不含在 AgentCore 帳單裡。

!區域與配額：兩個會擋住架構決策的地方

沒有台灣區。從台灣出發，東京（ap-northeast-1）是元件最齊的亞太區，唯一缺 Payments

Runtime V2 平台只有東京（新加坡、紐雪梨、首爾、孟買都沒有）。us-east-1 與 us-west-2 功能最完整、配額也最高。

⚠️ Web Search 的可用區域，官方文件前後不一致

區域表寫 us-east-1、愛爾蘭、東京；Harness 的 Tools 頁卻寫「只有 us-east-1」。要用 Web Search 前先確認目標區域。

沒有使用紀錄的帳號呼叫 CreateAgent 會收到 403，而且沒有例外申請管道

→導入前的七個檢查

  1. Harness 還是 Runtime？有沒有既存 agent 程式碼要搬，或 Harness 表達不了的編排需求
  2. 目標區域有沒有 V2、Payments、Web Search？東京缺 Payments，V2 只有東京
  3. session 設計：8 小時上限、15 分鐘同步逾時 —— 長任務是不是該走非同步
  4. 新 session 速率 25 TPS夠不夠尖峰流量
  5. 成本看的是 token 不是運算：Web Search、Evaluations、Policy 檢查次數、CloudWatch 日誌量才是要盯的項目
  6. Policy 掛在 Gateway：換框架時治理層不用重做，但要在 Gateway 前面確認 Cedar 規則
  7. Classic 遷移：逐階段 prompt override 與多 agent 協作沒有直接對應的替代品，要先想清楚
