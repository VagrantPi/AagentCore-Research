ELI5 · Senior Engineers · Amazon Nova Act

部署 = 註冊名字，另外找台機器跑

Nova Act 服務不幫你執行程式。它只認得 workflow definition，程式要自己丟到 AgentCore / Lambda / Fargate / ECS。

1「部署」是兩件獨立的事

1在 Nova Act 服務註冊 workflow definition：一個名字，加上選填的 S3 匯出設定。只做一次。
2把 Python 程式放到某個運算平台上跑。Nova Act 服務本身不排程、不跑容器。

兩者鬆耦合：同一個 definition 可以從本機、Lambda、AgentCore 各自執行，Console 都記在同一個名字底下 —— 拿來比較不同環境的行為很好用。程式端預設跑在 AgentCore Runtime（CLI）或 Lambda / Fargate / ECS（CDK 範例），瀏覽器是容器內的 headless Chromium 或 AgentCore Browser。

後端類比：definition 像 CI 系統的 pipeline 定義，run 像一次執行。definition 不含程式碼，程式碼在你的容器裡。

!CLI 官方明說：不要拿它上正式環境

act workflow create --name my-workflow                          # 註冊 definition
act workflow deploy --name my-workflow --source-dir ./project   # 建置並部署
act workflow run    --name my-workflow --payload '{"input": "data"}'
原話：「SHOULD NOT be used as a dependency in production code」

原因之一是部署狀態只存在你的個人電腦：~/.act_cli/state/{account}/{region}/workflows.json（有檔案鎖），建置產物在 ~/.act_cli/builds/{workflow}/ 且不會自動清除。換一台機器或換一個人就接不上 —— 跟早期 Terraform 用本機 state 是同一個問題。

CLI 自動建立的資源名稱
ECR repositorynova-act-cli-default（所有 workflow 共用）
IAM rolenova-act-{workflow}-role（可用 --execution-role-arn 換自己的）
S3 bucketnova-act-{account}-{region}（也是預設匯出位置）
入口的慣例：預設 main.py 裡必須有 def main(payload):

--entry-point 可換檔案；--skip-entrypoint-validation 會跳過檢查（等於關掉這層保護）。

!用 payload 傳 API key，密鑰會外洩

payload 裡的 AC_HANDLER_ENV 會在執行前被寫進 os.environ

官方範例拿它傳 NOVA_ACT_API_KEY。但走這條路，密鑰就會出現在呼叫端的程式碼、shell history 和可能的呼叫紀錄裡。

正式環境改用 IAM 驗證 —— 完全不需要 API key

其他密鑰（網站帳密、第三方 token）請用 Secrets Manager 或 AgentCore Identity，不要塞進 payload。

區域：Runtime 可以部署在別的區，Nova Act 服務只有 us-east-1

--region 決定 Runtime 在哪，但每一步模型推論都會跨區呼叫 us-east-1。這會同時增加延遲與跨區流量成本。

2四種運算平台：真正的天花板是平台，不是 Nova Act

平台適合架構重點限制
Lambda事件驅動、短流程容器映像檔預裝 Playwright最長 15 分鐘
Fargate一般長流程私有子網路 + VPC endpoint + NAT要自己管 VPC
ECS（EC2）大量、需控制主機自動擴展、加密的 EBS容量自己管
AgentCore要接其他 AgentCore 元件ARM64 容器、內建 OpenTelemetry見 04
✓選擇關鍵只有兩題：流程跑多久、要不要接 AgentCore 的其他元件。5 分鐘內事件觸發 → Lambda；要自己控制網路 → Fargate；要接 Identity / Browser / Observability → AgentCore。
!時長上限的實際排序：Lambda 15 分鐘 < AgentCore microVM 8 小時 < AgentCore Instances 14 天。而 Nova Act 的 act timeout 是 24 小時、workflow run 最長 1 週 —— 所以流程能跑多久，通常卡在運算平台。
!CDK 範例的瀏覽器參數全部相同：--disable-gpu --disable-dev-shm-usage --no-sandbox --single-process，一律 headless。

3exportConfig：軌跡只暫存，要自己寫進 S3

aws nova-act create-workflow-definition \
  --name my-workflow \
  --export-config '{"s3BucketName": "my-bucket", "s3KeyPrefix": "nova-act-workflows"}' \
  --region us-east-1
!服務只暫存 agent trajectory（prompt、截圖、模型回應）。要長期保存才設 exportConfig，把這些寫到自己的 S3。
!bucket 必須和呼叫端在同一個帳號，不支援跨帳號。呼叫端需要 s3:PutObject on arn:aws:s3:::{bucket}/{prefix}/*。
!官方強烈建議加密這個 bucket，因為截圖裡可能有個資。
✓也能用 Console、boto3 或 act workflow create 建立。只需要建立一次 —— 官方特別提醒不要在執行時建立 definition。

!CloudWatch 沒有「任務成功率」

namespace AWS/NovaAct 只有 5 個 API 層級指標：

指標單位說明
InvocationsCountAPI 請求數
Latencyms端到端延遲，可查 p50 / p90 / p99
UserErrorsCount參數錯誤、ID 錯誤、IAM 權限不足
SystemErrorsCount服務內部錯誤、相依服務失敗、逾時
ThrottlesCount被限流或超過配額
act 失敗在服務看來，可能只是一次正常的 API 呼叫

例如 ActAgentFailed —— API 層回應成功，但任務失敗。業務層級的成功率沒有內建指標，要自己從程式裡發自訂指標，或從 run 狀態統計。

維度只有 Workflow 和 ApiName 兩個

官方建議的告警：SystemErrors 超門檻、Latency p90/p99 上升、Throttles 只要出現就代表該申請提高配額。看不到 session / act 層級的分解。

!CloudTrail：資料面要自己開，而且有兩個 API 不在清單上

類型預設包含的 API
管理事件（控制面）有記錄CreateWorkflowDefinition、Get/List/DeleteWorkflowDefinition、GetWorkflowRun、ListWorkflowRuns、ListSessions、ListActs、ListModels
資料事件（資料面）要自己開CreateSession、CreateAct、UpdateAct、InvokeActStep（需 advanced event selectors）
!event source 是 nova-act.amazonaws.com。資料事件可用 ARN 過濾：arn:aws:nova-act:{region}:{account}:workflow-definition/{name}，或再加 /workflow-run/{runId}。
!資料面的請求可能含有個資，所以部分欄位被遮蔽 —— 稽核時看不到完整 payload。
怪地方：想稽核「誰觸發了哪次 run」，清單上找不到那兩個 API

CreateWorkflowRun 和 UpdateWorkflowRun 出現在配額表的資料面 API裡，但 CloudTrail 的兩張清單都沒有列出。要仰賴這個做稽核之前必須實測確認。

!文件矛盾與維運三瓶頸

!CDK README 自打架。「Prerequisites」要求準備 Nova Act API key（還要 export NOVA_ACT_API_KEY），但同一份文件的「Authentication」又說「All examples use IAM Role authentication — no API keys required」。從架構看應該走 IAM，API key 那段像是舊版殘留，需實測確認。
!沒有官方排程功能。批次（例如每天 1,000 筆）要自己設計扇出：用佇列控制併發，把 InvokeActStep 總速率壓在配額內。觸發方式取決於平台：CLI、InvokeAgentRuntime、EventBridge Scheduler、SQS、API Gateway。
!維運最常碰到的三個上限：① InvokeActStep 5 TPS（平行度天花板，看 Throttles）；② 每個 act 最多 200 步（max_steps 再大也超不過）；③ 運算平台自己的時長上限。
✓Console 的 run 詳情會顯示使用的 model ID —— 這是追查「模型升版後行為改變」的關鍵，搭配 00 的版本固定策略一起用。

→上正式環境前的六個檢查

  1. 正式環境有沒有用 CLI —— 換機器就斷的 state 只能拿來做原型
  2. 驗證走 IAM 還是 payload 傳 API key —— 密鑰不該出現在 shell history
  3. exportConfig 的 S3 有沒有加密、跟呼叫端同帳號 —— 截圖裡可能有個資
  4. CloudTrail 資料事件開了嗎 —— 沒開就稽核不到 InvokeActStep
  5. 任務成功率指標在哪 —— 內建沒有，得自己發
  6. 流程時長會撞到哪個上限 —— 多半是平台的 15 分鐘，不是 Nova Act 的 24 小時
