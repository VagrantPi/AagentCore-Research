# 延伸：Optimization 閉環的實際導入

> 接續 [07-evaluations](README.md#optimization從評估結果到改善)。這篇討論：怎麼把 system prompt 和工具說明搬進 configuration bundle；A/B test 需要多少樣本、跑幾天；Recommendations 產生的 prompt 要怎麼審查才上線；以及上線後怎麼回滾。
>
> 資料查核日期：2026-09-30。標示「推論」的部分是官方文件沒有明說、由我推導的。
>
> 本機工具：[experiments/ab-sample-size](experiments/ab-sample-size/)（樣本數與天數估算，已實跑）。

## 結論先講

- **Configuration bundle 就是「放在 AgentCore 上、有版本紀錄的 JSON 設定檔」**，沒有固定的 schema。把 prompt、模型 ID、工具說明從程式碼搬進去之後，改 prompt 就不必重新部署 agent。
- **工具說明可以完全不改程式碼：** Gateway 會在 `tools/list` 時直接換掉說明。System prompt 和模型設定則需要 agent 程式在每次請求時讀取 bundle。
- **A/B test 的統計部分幾乎是黑盒子：** 檢定方法沒寫、最小樣本數沒寫、不能設停止規則。官方範例裡實驗組只有 **6 個樣本**就被標成「顯著」。**樣本數要自己事先算，並且在達到之前不要看結果做決定。**
- **Recommendations 沒有審核流程：** 官方只說「由 LLM 產生，套用前請審查與測試」。建議的流程是：產生建議 → 人工審查 → 離線評估（batch 或 dataset）→ 小流量 A/B test → 推廣。
- **正式的上線與回滾靠 gateway rules，不是 A/B test。** A/B test 結束後，用 rule 把流量固定指向勝出的 bundle 版本；要回滾，就把 rule 改回舊版本。

## 第一步：把設定搬進 configuration bundle

### Bundle 的結構

```json
{
  "arn:aws:bedrock-agentcore:...:runtime/my-agent": {
    "configuration": {
      "system_prompt": "你是訂單客服……",
      "model_id": "global.anthropic.claude-sonnet-4-5-20250929-v1:0",
      "temperature": 0.2,
      "tools": {
        "lookup_order": {"description": "用訂單編號查詢訂單狀態與出貨資訊……"}
      }
    }
  }
}
```

- 最外層的 key 是**資源的 ARN**（runtime 或 gateway），值是一份**自由格式的 JSON**。`system_prompt`、`model_id`、`tools.<名稱>.description` 只是文件慣用的命名，不是強制的 schema。
- CLI 可以用 `{{runtime:<名稱>}}`、`{{gateway:<名稱>}}` 代替 ARN。
- **名稱不能有 `-`**（`[a-zA-Z][a-zA-Z0-9_]{0,99}`）。
- 每個 bundle 最大 5 MB、最多 10,000 個版本；每個帳號最多 1,000 個 bundle。

### 版本管理：類似 Git

- **每次更新都會產生一個新的、不可修改的版本**（UUID），帶有 `parentVersionIds`、`branchName`（預設 `mainline`）、`commitMessage`、`createdBy`。
- **有兩個 parent 就是合併**，跟 Git 的 merge commit 一樣。
- **更新時指定的 parent 不是該分支的最新版本，會回 `ConflictException`**，這就像 Git 的「非 fast-forward 推送被拒絕」，用來防止兩個人同時修改時互相覆蓋。
- CLI 有 `agentcore cb versions` 和 `cb diff --from --to`，可以比較兩個版本的差異。
- ⚠️ **文件矛盾：** 同一頁先說 `parentVersionIds`「更新 components 時必填」，後面又說「可以省略或只給一個 parent」。

### Agent 程式怎麼讀取

| 設定 | 誰負責套用 | Agent 程式要改嗎 |
|---|---|---|
| **工具說明** | **Gateway**，在回應 MCP 的 `tools/list` 時直接替換 | **不用改** |
| System prompt | Agent 程式 | 要改：每次請求讀 bundle，再組 prompt |
| 模型 ID、temperature | Agent 程式 | 要改：**每次請求重新建立 agent 物件**，或在框架的 hook 裡替換 |

Bundle 的 ARN 和版本是透過 W3C baggage header（`aws.agentcore.configbundle_arn`、`aws.agentcore.configbundle_version`）傳進來的。通常由 Gateway 注入，測試時也可以在 `invoke_agent_runtime` 手動帶入。

```python
from bedrock_agentcore.runtime import BedrockAgentCoreContext

DEFAULTS = {"system_prompt": "你是訂單客服……", "model_id": "...", "temperature": 0.2}

@app.entrypoint
def invoke(payload, context):
    try:
        cfg = {**DEFAULTS, **BedrockAgentCoreContext.get_config_bundle()}  # 沒有 bundle 時回傳 {}
    except Exception:
        cfg = DEFAULTS            # 讀取失敗會拋例外：要有預設值，不能讓 agent 因此掛掉
    agent = build_agent(**cfg)    # 每次請求依設定建立，模型 ID 和 temperature 才能被切換
    return agent(payload["prompt"])
```

- 需要 SDK ≥ 1.8；結果會快取。
- 如果只換 system prompt，Strands 可以用 `BeforeModelCallEvent` hook，不必每次重建 agent。
- **工具說明的替換只作用在 `tools/list`，不作用在 `invoke_tool` 和語意搜尋。** 開啟語意搜尋時，搜尋結果裡看到的仍然是**原本的**說明（推論：這會讓 A/B test 工具說明的結果失真）。
- **HTTP target 的 gateway 會忽略 baggage 裡的 bundle**，只有 MCP 路徑適用。
- Gateway 的 execution role 需要 `GetConfigurationBundleVersion` 權限。

### 程式改寫的清單（判斷）

1. **把 prompt 從程式碼抽出來**，程式碼裡只留預設值（也是 bundle 讀取失敗時的備援）。
2. **改成每次請求都讀設定**，不要在模組載入時就建立 agent。
3. **工具說明的「真相來源」只能有一個**：如果改由 bundle 管理，就不要再改程式碼裡的 docstring，否則兩邊會不一致。
4. **在 span 裡記下目前使用的 bundle 版本**（SDK ≥ 1.8 的 `BaggageSpanProcessor` 會自動加上 A/B test 的分組屬性），之後分析問題時才知道是哪個版本的 prompt。

## 第二步：Recommendations 產生候選版本

| 類型 | 輸入 | 需要評估器嗎 | 輸出 |
|---|---|---|---|
| `SYSTEM_PROMPT_RECOMMENDATION` | 目前的 prompt（直接給文字，或指定 bundle 的 JSON 路徑）+ trace 來源 | **需要剛好一個「有數值分數」的評估器**，當作最佳化的目標 | 新的 prompt + 說明 |
| `TOOL_DESCRIPTION_RECOMMENDATION` | 每個工具的說明 + trace 來源 | 不需要 | 每個工具的新說明 + 說明 |

- **Trace 來源**：CloudWatch Logs（可以加過濾條件，例如只看 `goal_success_rate < 0.5` 的 session）、直接提供 span、batch 評估的結果、online 評估的結果。
- **輸入是 bundle 時，結果會直接存成一個新的 bundle 版本**，但**不會自動啟用**。
- 每個 recommendation 只取樣 **20 個 session**，非同步執行，官方範例大約 2–5 分鐘。
- **Recommendations 本身免費**，只付它用到的評估費用。

### 審查才上線

官方對審查的說法只有一句：「Recommendations are generated by LLMs. Review and test before applying them.」所以審查流程要自己設計。

**人工審查時要看什麼（判斷）：**

| 檢查項目 | 為什麼 |
|---|---|
| **跟舊版的 diff**（`cb diff`） | LLM 改寫 prompt 時常常「順便」改掉不相關的部分 |
| **安全與業務約束有沒有被刪掉或弱化** | 最佳化目標只有一個分數，例如「任務成功率」；刪掉「金額不能超過上限」可能讓分數變高。**這類約束本來就應該放在 Policy（見 08），不該只靠 prompt** |
| **有沒有對 20 個樣本過度擬合** | 只看 20 個 session，建議可能是在修補那 20 個特例 |
| **語氣、品牌用語** | 評估器不一定會檢查 |
| **長度** | 更長的 prompt 代表每次呼叫更多 token |

**離線驗證（上 A/B test 之前）：**

1. 用 **batch 評估**，拿新舊兩版 bundle 對**同一批**歷史 session 或 dataset 評分。
2. **除了最佳化的目標指標，也要看其他指標有沒有變差**，例如 `Harmfulness`、`Refusal`、軌跡比對。只最佳化一個分數，最常見的副作用就是其他指標退化。
3. 通過離線驗證，才進 A/B test。

## 第三步：A/B test

### 設定

```python
variants = [
  {"name": "C",  "weight": 80, "variantConfiguration": {"configurationBundle": {"bundleArn": "...", "bundleVersion": "<舊版>"}}},
  {"name": "T1", "weight": 20, "variantConfiguration": {"configurationBundle": {"bundleArn": "...", "bundleVersion": "<新版>"}}},
]
evaluationConfig = {"onlineEvaluationConfigArn": "..."}
```

- **只能兩組**，名稱固定是 `C` 和 `T1`；**每個 gateway 同時只能有一個 A/B test**。
- **分組以 session 為單位，而且是固定的**（依 `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id`），同一個 session 不會一下 A 一下 B。
- **指標只能來自 online 評估器，而且必須是數值**；文字類別的量表不能用。
- 官方建議：**實驗期間把 online 評估的抽樣比例設成 100%**。
- 暫停會讓所有流量回到對照組；停止則是永久的。
- ⚠️ **文件矛盾：** 停止之後的流量，一頁說回到對照組，另一頁說回到「預設設定」。

### 結果長什麼樣子

```json
{"controlStats": {"variantName": "C", "sampleSize": 24, "mean": 0.72},
 "variantResults": [{"variantName": "T1", "sampleSize": 6, "mean": 0.85,
   "absoluteChange": 0.13, "percentChange": 18.1, "pValue": 0.032,
   "confidenceInterval": {"lower": 0.02, "upper": 0.24}, "isSignificant": true}]}
```

- `isSignificant` 的定義是「p 值 < 0.05，**而且樣本數足夠**」，但**「足夠」是多少沒寫**，範例裡 6 個樣本就被標成顯著。
- **沒有寫用哪一種檢定**，不能設定 alpha、停止規則、最小可偵測差異（MDE）、實驗時長。
- `GetABTest` 會回傳 `maxDurationExpiresAt`，代表實驗會自動到期，但**時長是多少、能不能設定，文件都沒寫**。

### 樣本數要自己算

**「偷看」問題：** 如果每天看一次結果，一看到「顯著」就停，誤判的機率會遠高於 5%。官方文件說「輪詢結果不影響有效性」，這個說法**忽略了這個問題**（判斷）。正確做法是**事先算好樣本數，達到之前不做決定**。

`sample_size.py` 的計算結果（雙尾、alpha = 0.05、檢定力 0.8、每天 2,000 個 session）：

| 指標 | 想偵測的差異 | 每組需要的 session 數 | 50/50 分流 | 80/20 分流 | 80/20 + 評估只抽 10% |
|---|---|---|---|---|---|
| 通過率 0.70 → 0.80 | +10 個百分點 | 294 | 1 天 | 1 天 | 8 天 |
| 通過率 0.70 → 0.75 | +5 個百分點 | 1,251 | 2 天 | 4 天 | **32 天** |
| 通過率 0.70 → 0.72 | +2 個百分點 | 8,080 | 9 天 | 21 天 | — |
| 連續分數，標準差 0.25 | +0.05 | 393 | 1 天 | 1 天 | 10 天 |

（「80/20 + 評估只抽 10%」那欄，0.70 → 0.75 是實際跑出來的 32 天；其餘由同一個公式推算。）

怎麼讀：

- **想偵測的差異越小，需要的樣本數增加得越快**（跟差異的平方成反比）。從 +5 個百分點降到 +2 個，樣本數變成 6 倍多。
- **瓶頸在流量少的那一組。** 80/20 分流比 50/50 慢一倍多，但風險比較低（只有 20% 的使用者用到新版）。
- **online 評估的抽樣比例會直接乘上去。** 平時抽 10% 很合理，但實驗期間要調到 100%，否則實驗會拖很久。
- **每個被評估的 session 都要付評估費。** 以每次評估約 $0.04 計算，2,500 個 session × 1 個評估器 ≈ $100；如果掛 3 個評估器，就是 $300。

**實驗天數的經驗法則（判斷）：** 就算樣本數早就夠了，也至少跑**完整的一週**，涵蓋平日和週末的使用者差異。

### 決定上線

```
達到預先算好的樣本數 → 看主要指標（顯著且信賴區間下限 > 0）
                    → 看護欄指標（Harmfulness、Refusal、延遲、成本）沒有變差
                    → 推廣
```

- **推廣只有 CLI 有**：`agentcore promote ab-test` 會改寫 `agentcore.json`，然後要 `agentcore deploy`。**SDK 沒有「推廣」這個操作**，用 IaC 管理的話要自己更新 bundle 版本的引用。

## 第四步：用 gateway rules 做正式的上線與回滾

A/B test 是用來**做決定**的；正式的流量控制要用 **gateway rules**：

| 用途 | Rule 的設定 |
|---|---|
| 固定使用某個版本 | `configurationBundle.staticOverride {bundleArn, bundleVersion}` |
| 漸進式上線（canary） | `weightedOverride`，兩個版本，權重 1–99，例如 95/5 → 80/20 → 50/50 → 0/100 |
| 只給特定呼叫者用新版 | 條件 `matchPrincipals`（**只支援 IAM ARN，不支援 JWT claim**） |
| **回滾** | **把 rule 指回舊的版本 ID** |

- 每個 gateway 最多 20 條 rule，優先順序 1–1,000,000。
- **Bundle 的版本不可修改，所以回滾是可靠的**：舊版本永遠還在，指回去就好。
- **判斷：** 把 bundle 的版本 ID 也放進 Git（例如 IaC 的變數），這樣「現在正式環境用的是哪個 prompt」在 Git 裡有紀錄，回滾也可以走一般的部署流程。

## 完整的閉環

```
Online 評估（平時抽樣 10%）
   │ 發現某指標下降，或定期檢視
   ▼
Recommendations（過濾出低分 session 當輸入）→ 新 bundle 版本（未啟用）
   │
   ▼
人工審查 diff（約束有沒有被刪、有沒有過度擬合）
   │
   ▼
Batch 評估：新舊版本對同一批 session，主要指標 + 護欄指標
   │
   ▼
A/B test（online 抽樣調到 100%，跑到預先算好的樣本數、至少一週）
   │
   ▼
Gateway rule 漸進上線 → 全量；有問題就把 rule 指回舊版本
```

## 配額（都不能調整）

| 項目 | 值 |
|---|---|
| A/B test | 每個 gateway 1 個、2 組；每個帳號同時 20 個 |
| Recommendations | 同時 5 個；每次取樣 20 個 session；prompt 最長 20,000 字元 |
| Bundle | 每帳號 1,000 個；每個 bundle 10,000 個版本；5 MB |
| Gateway rules | 每個 gateway 20 條 |
